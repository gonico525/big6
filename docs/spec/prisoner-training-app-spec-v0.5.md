# プリズナートレーニング継続アプリ 仕様書

- 版数: v0.5
- 作成日: 2026-08-12
- 位置づけ: 個人利用（自分用）。公開・配布は想定しない

**v0.4からの変更点**
- PWA化（拡張計画の段階2）を実装済みとし、仕様に反映（2.1、6.1、6.4、6.5）

- 新しい版が待機している場合の更新バナーをホームに追加（5.2）
- 設定に「アプリ」（ホーム画面への追加、オフライン動作の状態）を追加（5.4）

**v0.3からの変更点**
- 片側種目（片腕・片脚）に対応。左右共通のステップ・級で扱う（3.4、3.6、5.5）
- ステップごとのカウント方式 `mode`（rep / hold / free）を追加（3.6、5.5）
- 実行途中に離脱した場合の復帰仕様を追加（5.5）
- ステップ降格の提案を追加（4.6）
- 日付の確定基準、単位・モードがステップ間で変わる場合の扱いを明記
- テンポの種目別上書きは設けない（書籍に種目別の秒数指定がないため）

## 1. 目的と背景

### 1.1 解決したい課題

| 課題 | 内容 |
|---|---|
| 記録の面倒さ | 毎回セット数・回数を入力するのが負担になり離脱する |
| 習慣化の失敗 | 週2回の実施そのものが定着しない |

以下は課題として該当しないため、優先度を下げる。

- 昇格判断への迷い（書籍の基準で判断可能）
- 動作テンポ・呼吸の理解（既知）

### 1.2 設計方針

**「記録アプリ」ではなく「実行アプリ」として作る。**

記録の面倒さの本質は、入力操作そのものよりも「今日は何をどれだけやるか」を毎回判断させられることにある。本アプリは、起動時点で実施内容が確定表示されており、実行完了が最小操作で記録される構造をとる。

**入力の手間と、保存するデータの粒度は分離する。**
画面上はタップ操作のみで完了しても、内部では昇格判定に必要な粒度のデータを保存する。

### 1.3 既存アプリを採用しない理由

調査対象: Convict Conditioning Tracker（iOS）、CC Tracker（Android）、GitHub上のオープンソース実装。

- UIが英語のみ
- 更新が長期間停止している
- 記録が主目的で、実施内容の自動提示がない（毎回の判断が発生する）
- 週単位での消化状況の可視化が弱い

## 2. スコープ

### 2.1 実装するもの

- BIG6の種目別の実施記録（片側種目を含む）
- 当日の目標の自動提示（級内の漸進、級の移行、ステップ昇格を含む）
- レップのテンポカウント（音＋リング表示）
- セット間の休憩カウントアップ
- 実行途中で離脱した場合の復帰
- 週単位の実績表示
- 昇格提案・降格提案
- 未解禁種目の推奨表示
- 進捗グリッド（6種目×10ステップ）と履歴の閲覧
- 記録の追加（遡及入力）・修正・削除
- 設定画面
- データのエクスポート／インポート（JSON）
- ホーム画面への追加とオフライン動作（PWA。6.5）

### 2.2 実装しないもの

| 項目 | 理由 |
|---|---|
| 通知・リマインダー | PWAのローカル通知は挙動が不安定。Web Pushはプッシュサーバが必要で、個人利用に対して複雑度が過大。OS標準のアラーム／カレンダーで代替 |
| 連続実施日数（ストリーク） | 途切れた際に離脱の引き金になるため。週単位の実績表示で代替 |
| アカウント／サーバ同期 | 個人利用のため不要。端末間移行はJSONエクスポートで対応 |
| ウォームアップセットの記録 | 記録対象はワークセットのみ |
| 過去データの移行機能 | 現時点で移行対象なし |
| 左右別のステップ管理 | 書籍の進め方と合わず、進捗表示も倍増するため（4.7参照） |

## 3. データモデル

### 3.1 設計原則

**「後から復元できない情報のみを保存する」**

導出可能な値はレコードに保存せず、判定時に算出する。

| 情報 | 保存 | 理由 |
|---|---|---|
| 各セットの実績値 | する | その日の実績であり復元不可能 |
| 当日目標 | する | 前回実績から動的に決まる状態であり復元不可能 |
| 単位（回数／秒） | する | 数値だけでは判別不可能 |
| ステップ番号 | する | 実施時点のステップは復元不可能 |
| ステップ昇格・降格の履歴 | する | 利用者のタップによる決定であり復元不可能 |
| 級 | しない | 初期値と履歴から常に導出可能（4.5参照） |
| 関門基準値 | しない | 種目・ステップ・級から常に導出可能 |
| 解禁状態 | しない | 他種目の現在ステップから常に導出可能 |
| 種目の手動有効化 | する | 利用者の判断結果であり導出不可能（設定として保持） |

### 3.2 実施記録レコード

1回のワークアウトにおける1種目分を1レコードとする。

**両側同時の種目**

```json
{
  "id": "2026-08-12-pushup-1",
  "date": "2026-08-12",
  "exercise": "pushup",
  "step": 3,
  "unit": "reps",
  "perSide": false,
  "sets": [20, 20, 18],
  "targetOfDay": { "sets": 2, "value": 20 },
  "achieved": true
}
```

**片側種目（片腕・片脚）**

```json
{
  "id": "2026-08-12-pushup-1",
  "date": "2026-08-12",
  "exercise": "pushup",
  "step": 8,
  "unit": "reps",
  "perSide": true,
  "sets": [[10, 9], [10, 8]],
  "targetOfDay": { "sets": 2, "value": 10 },
  "achieved": false
}
```

| フィールド | 型 | 内容 |
|---|---|---|
| `id` | string | 一意キー。日付＋種目＋連番 |
| `date` | string | 実施日（YYYY-MM-DD、ローカル日付）。**開始時刻の日付で確定する**（深夜をまたいでも変えない） |
| `exercise` | string | 種目識別子 |
| `step` | number | 実施時のステップ（1〜10） |
| `unit` | string | `reps`（回数）／ `sec`（秒） |
| `perSide` | boolean | 片側種目かどうか |
| `sets` | number[] \| [number, number][] | 各セットの実績値。`perSide: true` の場合は `[左, 右]` のペア |
| `targetOfDay` | object | 実施時に提示された目標。`perSide` の場合、`value` は**片側あたり**の値 |
| `achieved` | boolean | 目標達成の可否。片側種目では**左右とも満たした場合のみ true** |

**補足**

- 目標どおり完了した場合も `sets` に実績値として書き込む。UIの操作量は変えずに判定材料を確保する。
- 1日に同一種目を複数回実施した場合は別レコード（`id` の連番で区別）。
- 遡及入力で追加したレコードも同一形式。`targetOfDay` は入力値から補完する。

### 3.3 ステップ変更イベント

```json
{
  "date": "2026-09-15",
  "exercise": "pushup",
  "from": 3,
  "to": 4,
  "type": "promote"
}
```

`type` は `promote`（昇格）／ `demote`（降格）／ `manual`（設定画面からの手動変更）。

**保存する理由**

1. `minWeeksPerStep`（同一ステップでの最低経過週数）の判定基準を安定させるため。「そのステップの最初の記録日」で代用すると、記録なしで手動変更した場合に破綻する
2. 降格・手動修正の経緯を残すため

### 3.4 種目マスタ

| 識別子 | 表示名 | 分類 | 開始フェーズ |
|---|---|---|---|
| `pushup` | プッシュアップ | ビッグフォー | `down`（下げる） |
| `squat` | スクワット | ビッグフォー | `down`（下げる） |
| `pullup` | プルアップ | ビッグフォー | `up`（上げる） |
| `legraise` | レッグレイズ | ビッグフォー | `up`（上げる） |
| `bridge` | ブリッジ | 後期追加 | `up`（上げる） |
| `handstand` | ハンドスタンド・プッシュアップ | 後期追加 | `down`（下げる） |

**開始フェーズ（`startPhase`）**

レップの開始方向は種目によって異なる。プッシュアップやスクワットは静止した高い位置から下げて始まるが、プルアップはデッドハング、レッグレイズは脚を下ろした状態から上げて始まる。

テンポ再生の順序はこの値から組み立てる（5.5参照）。設定画面から変更可能。

### 3.6 ステップマスタ（standards）

各ステップは以下を持つ。基準値は初級・中級・上級の3つで、それぞれ「セット数×値」で規定される。

```json
"standards": {
  "pushup": {
    "8": {
      "unit": "reps",
      "mode": "rep",
      "perSide": true,
      "levels": {
        "1": { "sets": null, "value": null },
        "2": { "sets": null, "value": null },
        "3": { "sets": null, "value": null }
      }
    }
  }
}
```

| 属性 | 値 | 内容 |
|---|---|---|
| `unit` | `reps` / `sec` | 回数か保持秒数か |
| `mode` | `rep` / `hold` / `free` | カウント方式（下記） |
| `perSide` | boolean | 左右を分けて行うか |
| `levels` | object | 級ごとの基準値。1=初級 / 2=中級 / 3=上級 |

**カウント方式（`mode`）**

| mode | 挙動 | 想定 |
|---|---|---|
| `rep` | テンポカウント。リングが1レップ周期で一周 | 大半のステップ |
| `hold` | 目標秒数でリングが一周 | 保持系のステップ |
| `free` | カウントなし。終了後に実績を手入力 | レップの4フェーズに分解できない動作（ウォールウォーキング等） |

`unit` と `mode` は独立して指定する。単位が回数でもテンポカウントが適さない動作があるため。

**基準値・属性はアプリに同梱せず、利用者が書籍を参照して入力する。** 書籍の基準表を再配布しないため、および版による差異に対応するため。

入力は**初回に一括入力画面でまとめて行う**（生涯1回）。入力済みの値は保存領域に永続化され、以降は参照のみ。設定画面からいつでも修正可能。

未入力のステップは、該当種目のカード上に入力欄を表示して促す。

**ステップ間で `unit` や `mode` が変わる場合**（保持系から回数系へ移行する等）、昇格直後の初期目標は新ステップの初級基準に対して `initialRatio` を適用する。前ステップの実績は参照しないため、単位が変わっても破綻しない。

### 3.7 初期状態

履歴がない状態では級を導出できないため、初期値を種目ごとに指定する。

```json
"initialState": {
  "pushup":    { "step": 3, "level": 2 },
  "squat":     { "step": 2, "level": 1 },
  "pullup":    { "step": 3, "level": 1 },
  "legraise":  { "step": 2, "level": 1 },
  "bridge":    { "step": 1, "level": 1 },
  "handstand": { "step": 1, "level": 1 }
}
```

### 3.8 設定

```json
{
  "unlockStep": 5,
  "maxIncrement": 2,
  "secIncrement": 5,
  "initialRatio": 0.8,
  "promotionCount": 4,
  "minWeeksPerStep": 4,
  "demoteThreshold": 2,
  "weekStart": "mon",
  "tempo": { "up": 2, "down": 2, "holdTop": 1, "holdBottom": 1 },
  "sound": { "enabled": true, "volume": 0.7 },
  "restBeepInterval": 10,
  "manuallyUnlocked": []
}
```

| キー | 初期値 | 内容 |
|---|---|---|
| `unlockStep` | 5 | ブリッジ・ハンドスタンドを推奨表示に切り替えるビッグフォーのステップ |
| `maxIncrement` | 2 | 回数系の1回あたり増加量の上限 |
| `secIncrement` | 5 | 秒数系の1回あたり増加量（秒） |
| `initialRatio` | 0.8 | ステップ昇格直後の初期目標の係数 |
| `promotionCount` | 4 | 昇格提案に必要な上級基準の達成回数 |
| `minWeeksPerStep` | 4 | 昇格提案に必要な同一ステップでの最低経過週数 |
| `demoteThreshold` | 2 | ステップ降格を提案する目標降格の発生回数 |
| `weekStart` | `mon` | 週の開始曜日 |
| `tempo` | 各2/1秒 | レップのテンポ。**順序ではなく意味で保持する**。アプリ全体で共通 |
| `sound` | on / 0.7 | 音のON/OFFと音量 |
| `restBeepInterval` | 10 | 休憩中のビープ間隔（秒） |
| `manuallyUnlocked` | `[]` | 推奨を無視して有効化した種目 |

**テンポを意味で保持する理由**

`up` / `down` / `holdTop` / `holdBottom` として持ち、再生順は種目の `startPhase` から組み立てる。順序で保持すると、上げ始まりの種目（プルアップ等）で上げと下げが入れ替わる。

**種目別の上書きは設けない。** 書籍に種目別の秒数指定がないため、全体で1つとする。必要になった場合は種目マスタ側に `tempo` を追加することで対応可能。

## 4. ロジック

### 4.1 当日目標の算出

起動時、種目ごとに直近の実施記録から算出する。判定は以下の順に行う。

#### (a) ステップ昇格・降格の直後

```
セット数 = 新ステップ 初級基準のセット数
値       = floor(新ステップ 初級基準の値 × initialRatio)
```

前ステップの実績からは換算できない（動作自体が変わるため）。`unit` や `mode` が変わる場合も同様に扱う。

#### (b) 直前の実施で現在の級の基準を満たした場合（級の移行）

級が上がるとセット数が増え、1セットあたりの値は下がる。

```
セット数 = 新しい級の基準セット数
値       = floor(前の級の基準値 × 前の級の基準セット数 ÷ 新しい級の基準セット数)
```

前の級の総量を新しいセット数で割り直す。新しい級の総量は前の級以上であるため、算出値が新しい級の基準値を超えることは原理的にない。

**ただし基準値は手入力であるため、入力ミスにより総量が逆転する可能性がある。算出値が新しい級の基準値を超えた場合は基準値でクランプする（保険）。**

例:
```
初級  1セット × 30  達成
  ↓
      2セット × 15   ← floor(30 × 1 ÷ 2)
  ↓  漸進
中級  2セット × 20  達成
```

#### (c) 通常の漸進

```
前回 achieved = true
  → 値を +maxIncrement（秒数系は +secIncrement）
  → 現在の級の基準値でクランプ

前回 achieved = false
  → 同じ目標を据え置く

直近2回連続で achieved = false
  → 前回実績の平均値を新しい目標値とする（目標の降格）
```

片側種目では、左右の実績のうち**低い方**を基準に判定する。

#### (d) 履歴がない場合

`initialState` のステップ・級から、その級の基準値を目標とする。

**遡及入力との関係**: 目標算出は常に「日付順で最新のレコード」を参照する。遡及入力によって過去に提示した目標を再計算し直すことはしない。

### 4.2 昇格提案

以下をすべて満たした場合のみ、種目カードに昇格提案を表示する。

1. 現在ステップの**上級基準**（セット数・値の両方）を満たす実績がある
2. 上級基準の達成が `promotionCount`（初期値4）回以上ある
3. 現在ステップの開始から `minWeeksPerStep`（初期値4）週以上経過している

3は書籍の「各ステップに最低1ヶ月」の推奨に対応する。**ロジックは急かす方向ではなく、進行を止める方向に使う。**

提案は表示のみ。昇格の実行は利用者のタップによる（自動昇格はしない）。実行時に3.3のイベントを記録する。

### 4.3 解禁判定

ブリッジ・ハンドスタンドは、ビッグフォー4種目すべてが `unlockStep`（初期値5）以上に到達するまで「まだ推奨されません」と表示する。

**ハードなロックにはしない。** 未解禁カードをタップすると理由が表示され、そこから実施を開始できる。開始した種目は `manuallyUnlocked` に追加され、以降は通常表示。

**背景**: 書籍のプログラム構成上、初期段階では6種目すべてを実施せず、ビッグフォーを先行させる。追加のタイミングについては解釈に幅があり（Step5／6／7の各説がある）、しきい値は設定値として外部化する。

### 4.4 週の集計

- 週は月曜始まり（`weekStart`）
- 種目ごとに当該週の実施回数を表示（**目標回数は表示しない。実績のみ**）
- ホーム上部に全体の実施回数を表示

**設計意図**: 6種目をまとめて実施できない場合があるため、実施単位を「日」ではなく「週」とする。日単位の達成/未達成を作らないことで、1日の未実施が離脱につながる構造を回避する。

### 4.5 級の判定

```
現在の級 = max( initialState の級, 履歴から導出した級 )
```

履歴から導出した級は「現在ステップにおいて、達成済みの最も高い級 + 1」（上級達成済みなら上級のまま、昇格待ち）。

初期値を下限として扱うことで、アプリ導入前の到達状況を反映する。

**留意点**: 基準値は手入力であるため、後から基準値を修正すると過去の級判定が遡って変わる。誤入力の訂正としては正しい挙動であり、個人利用のため許容する。

### 4.6 降格提案

同一ステップで**目標の降格（4.1(c)の3番目）が `demoteThreshold`（初期値2）回以上発生した場合**、ステップを1つ下げる提案を表示する。

**設計意図**: 目標値を下げ続けても、ステップ自体が身体に合っていない場合は解決しない。書籍が警告する「進みが速すぎること」への対処として、後退の導線を用意する。

提案は表示のみ。実行は利用者のタップによる。実行時に3.3のイベント（`type: "demote"`）を記録する。

### 4.7 片側種目の扱い

**左右で共通のステップ・級を用いる。** 左右別のステップ管理は行わない。

| 項目 | 扱い |
|---|---|
| 目標値 | 片側あたりの値（書籍の基準表記に準拠） |
| 達成判定 | **左右とも基準を満たした場合のみ達成**（弱い側に合わせる） |
| 漸進・級移行 | 左右共通の値で計算 |
| 進捗グリッド | 種目あたり1行（左右で分けない） |

**理由**: 左右別に管理すると進捗表示が120マスとなり、書籍の進め方とも一致しない。利き手側が先行するのは自然だが、弱い側を基準にすることで左右差の拡大を防ぐ。

## 5. 画面仕様

### 5.1 画面構成

```
ホーム ─┬─ 種目実行
        ├─ 進捗
        └─ 設定
```

| 画面 | 役割 |
|---|---|
| ホーム | 今日やること |
| 種目実行 | 実行と当日の記録 |
| 進捗 | これまでの記録（可視化・閲覧・追加・修正） |

進捗グリッドをホームに置かないのは、ホームの役割（今日やること）と情報の性質が異なり、情報過多になるため。

### 5.2 ホーム

```
┌──────────────────────────┐
│ 今週 7回                      [進捗] │
├──────────────────────────┤
│ スクワット                          │
│ Step2  ジャックナイフ・スクワット     │
│                                      │
│          2セット × 15回              │
│                                      │
│ 今週 0回          前回 6日前         │
├──────────────────────────┤
│ プッシュアップ                       │
│ Step8  ハーフ・ワンアーム・プッシュアップ │
│                                      │
│      2セット × 左右各10回            │
│                                      │
│ 今週 1回          前回 3日前         │
├──────────────────────────┤
│ ブリッジ      まだ推奨されません  ▸  │
│ ハンドスタンド  まだ推奨されません  ▸  │
└──────────────────────────┘
```

**要件**

- カードの表示項目: 種目名 / ステップ番号 / ステップ名 / 当日目標 / 今週の実施回数 / 前回実施日
- 片側種目は「左右各◯回」と明示する
- 当日目標を主役とし、週実績・前回実施日は補助情報として小さく配置する
- **前回実施日は相対表示**（「3日前」）。中1日ガードの判断材料を兼ねる
- 並び順: **今週の実施回数が少ない順 → 同数なら前回実施日が古い順**
- 昇格提案・降格提案がある場合、該当カードにボタンを表示
- 基準値が未入力の場合、該当カードに入力欄を表示
- 未解禁種目は下部に薄く表示。タップで理由を表示し、そこから開始可能
- カードのタップは**種目実行画面への遷移のみ**。実行は開始しない
- 上部に進捗画面への導線を置く
- 新しい版が待機している場合、カード群の上に更新バナーを表示する（6.5）。
  更新は自動では適用せず、ボタンを押したときだけ再読み込みする

### 5.3 進捗

#### (a) グリッド

6種目 × 10ステップ。

| 情報 | 表現 |
|---|---|
| 級 | **色相**（同系統でずらす） |
| 級内の進捗 | **塗り面積**（下から上へ満ちる） |
| 昇格可能 | **アクセント色**（琥珀系） |

```
未着手        枠線のみ
初級          淡いブルー
中級          標準ブルー
上級          深いブルー
昇格可能      琥珀（アクセント）
```

**昇格可能のみアクセント色とする理由**: 他の状態は現在地の表示だが、この状態のみ利用者の行動を待っている。同系統の最も深い色にすると60マスの中で埋没するため、例外的に色相を変える。

現在のステップは枠線を強調する。種目ごとの色分けは行わない（級の色相と競合するため）。

#### (b) 履歴リスト

グリッドのマスをタップすると、そのステップの実施記録を新しい順に表示する。

```
8/12  2×20, 18            目標 2×20        達成
8/09  2×(10/9), (10/8)    目標 2×左右各10   未達
8/05  2×19, 15            目標 2×19        未達
```

片側種目は `(左/右)` の形式で表示する。

#### (c) 記録の追加（遡及入力）・修正・削除

**専用画面は設けず、進捗画面に統合する。**

- **追加**: 「記録を追加」から、日付・種目・ステップ・セット実績を直接入力
- **修正・削除**: 履歴の行をタップして編集

**種目実行画面に日付欄を設けない理由**: 実施し忘れた日の入力ではテンポカウントを回す必要がなく、実行フローと噛み合わないため。記録の管理はすべて進捗画面に寄せる。

### 5.5 種目実行

```
[ プッシュアップ / Step3 ニーリング・プッシュアップ ]

  目標   2セット × 19回
  テンポ 下げ2 - 止め1 - 上げ2 - 止め1

        ┌──────────┐
        │  スタート  │
        └──────────┘

  1セット目  —
  2セット目  —
```

#### (a) テンポカウント（`mode: rep`）

スタートボタンで開始。

**フェーズの順序は種目の `startPhase` で決まる。**

```
startPhase = down （プッシュアップ／スクワット／ハンドスタンド）
  下げる → 下で止める → 上げる → 上で止める

startPhase = up （プルアップ／レッグレイズ／ブリッジ）
  上げる → 上で止める → 下げる → 下で止める
```

- **音**: 毎秒、短いビープ（同一音）。**レップの先頭のみ別の音**（低め・長め）
- **画面**: 現在フェーズの表示（「下げる」「止める」等）と、1レップ周期で一周するリングアニメーション
- **カウント**: レップの最終フェーズ（静止）を完了した時点で +1。進行中のレップは数えない
- **自動停止しない**: 目標回数に達してもカウントを継続する（超過分も記録するため）

フェーズの判別は画面表示に任せ、音は秒の刻みとレップの区切りのみを担う。テンポを変更しても音の設計は変わらない。

#### (b) 保持のカウント（`mode: hold`）

- リングは**目標秒数で一周**する
- 毎秒のビープは同様に鳴らす
- 限界時に操作できないため、**終了操作は行わず、落ちた後に経過秒を手入力**する（カウント音で自己計測できることを前提とする）

#### (c) カウントなし（`mode: free`）

- リング・テンポカウントを行わない
- 実施後に実績値を手入力する
- レップの4フェーズに分解できない動作（ウォールウォーキング等）に用いる

#### (d) 片側種目（`perSide: true`）

1セットを「左 → 右」の2ブロックで構成する。

```
  1セット目
    左  [ スタート ]   → 完了 → 実績確定
    右  [ スタート ]   → 完了 → 実績確定
  （セット完了）
```

- ブロックごとにテンポカウントを回す
- 左右の間にも休憩ボタンを出す
- 目標は片側あたりの値。**左右とも満たした場合のみ達成**

#### (e) セット完了

「終了」ボタン、または目標到達後の任意のタイミングで終了。確認画面を表示する。

```
    17 回で終了

      [ − ]  17  [ + ]

        [ 記録する ]
```

限界時に即座に操作できないことを前提とし、**押下が数レップ遅れても、その場で減算できる**ようにする。

#### (f) 休憩

セット完了後（片側種目では左右の間にも）「休憩」ボタン。

- **カウントアップ形式**。00:00から加算
- `restBeepInterval`（初期値10秒）ごとにビープ
- 休む長さは利用者が経過時間を見て判断する
- 次のセットのスタートで停止

将来カウントダウンに変更する可能性があるため、**経過秒を返す共通タイマーを1つ実装し、表示形式と通知条件のみを切り替える**構造とする。

#### (g) 途中で離脱した場合

セット完了ごとに**未確定レコード**を保存領域に書き込む。

次回起動時に未確定レコードが存在する場合、選択肢を提示する。

```
  8/12 プッシュアップ の記録が途中です
  （1セット目 20回 まで完了）

  [ 続きから ]  [ ここまでを記録 ]  [ 破棄 ]
```

- **続きから**: 残りのセットを実行する
- **ここまでを記録**: 完了済みのセットのみでレコードを確定する（`achieved` は基準に照らして判定）
- **破棄**: 未確定レコードを削除する

日付は**開始時刻の日付**のまま確定する。

#### (h) 技術的留意点

- 音はWeb Audio APIで生成する（音声ファイル不要）
- iOSは初回の音出しにユーザー操作を要するため、スタートボタンで解除する
- 実行中・休憩中はWake Lock APIで画面を維持する（画面消灯でタイマーの音が停止するため）
- バックグラウンド復帰時はタイマーの経過時間を実時刻から再計算する（タブ休止による遅延を補正）

## 6. 技術構成

### 6.1 ファイル構成

```
index.html
app.js          … 画面と状態管理
logic.js        … 目標算出・昇格判定・降格判定・解禁判定
timer.js        … テンポカウント・休憩タイマー・音生成
store.js        … 保存の抽象化
pwa.js          … Service Workerの登録・更新検知・ホーム画面追加（6.5）
sw.js           … Service Worker本体（6.5）
manifest.json   … ウェブアプリマニフェスト（6.5）
icons/          … アプリアイコン（SVGが原本、PNGは書き出し）
standards.json  … ステップマスタの空テンプレート（名称・unit・mode・perSide・基準値）
style.css
```

単一ファイル構成は採用しない。テンポエンジン、音声生成、グリッド描画、ステップマスタの一括入力UIを含めると規模が大きく、保守性が下がるため。単一ファイルの利点（ファイルを直接開ける）はGitHub Pages前提では不要であり、PWA化によりmanifestとService Workerも加わっている。

`pwa.js` はブラウザAPIのみを扱い、DOMには触れない。バナー・ボタンの描画は `app.js` が担う（`timer.js` と同じ切り分け）。

`standards.json` は初期テンプレートとしてのみ使用する。実際の値は保存領域に持つ。

### 6.2 ホスティング

GitHub Pages（HTTPS）。

Wake Lock API・Service Worker等がHTTPS配信を前提とするため、およびスマートフォンから設定を変更できるようにするため（`localhost` は例外として動作する）。

ビルド工程を持たないため、リポジトリの内容がそのまま公開物となる。

### 6.3 ストレージ抽象化

```js
const store = {
  load(),     // 全データの読み込み
  save(data), // 全データの保存
  export()    // JSON文字列の出力
};
```

`localStorage` への直接アクセスをコード内に散在させない。Capacitorでのネイティブ化時、WebViewのlocalStorageはOSによって回収される可能性があるため、差し替え範囲を1ファイルに限定する。

### 6.4 拡張計画

| 段階 | 内容 | 前提 | 状態 |
|---|---|---|---|
| 1 | 静的サイト + GitHub Pages | — | 実装済み |
| 2 | PWA化（ホーム画面追加、オフライン動作） | 1完了 | 実装済み（6.5） |
| 3 | Capacitorによるネイティブ化 | 2完了。ストレージをPreferences/SQLiteへ差し替え | 未着手 |

### 6.5 PWA

**目的**: ホーム画面から単体アプリとして起動できること、および通信のない場所（ジム・地下）でも起動できること。実行アプリである以上、その場で開けないことは機能欠損に等しい。

#### マニフェスト

| 項目 | 値 | 理由 |
|---|---|---|
| `name` / `short_name` | プリズナートレーニング / BIG6 | ホーム画面のラベルは短い方を使う |
| `start_url` / `scope` | `./` | GitHub Pagesのサブパス（`/big6/`）配信に追随させるため、絶対パスにしない |
| `display` | `standalone` | ブラウザUIを外し、実行中の誤操作を減らす |
| `orientation` | `portrait` | 実行画面は縦持ち前提 |
| `background_color` / `theme_color` | `#12161c` | 起動時のちらつきを抑える |
| `icons` | 192 / 512 / maskable 512 / SVG | Androidのアダプティブアイコン用に `maskable` を別に持つ |

iOSはマニフェストの `display` を参照しないため、`apple-mobile-web-app-capable` 等のメタタグを併記する。アイコンの原本はSVGとし、PNGはそこから書き出す。

#### キャッシュ方針

**stale-while-revalidate**（キャッシュを即座に返し、裏で取り直して次回に備える）。

- 対象は同一オリジンの GET のみ。アプリシェル（HTML・JS・CSS・マニフェスト・アイコン・`standards.json`）はインストール時に先読みする
- **ビルド工程がなくファイル名にハッシュが付かない**ため、配信のたびに版を上げなくても更新が届く方式を採る
- 代償として、**配信内容の反映は次回起動時**になる
- 配信するファイルを増やした場合は、先読みの一覧にも加える（漏れるとオフラインで欠ける）

#### 更新の適用

`sw.js` 自体が変わると新しいService Workerが待機状態になる。これを検知したらホームに更新バナーを出し、**利用者が押したときにだけ**切り替えて再読み込みする。

自動で再読み込みしないのは、実行中に画面が作り直されるとテンポカウントが中断されるため。同じ理由で、実行画面の表示中はPWAの状態変化による再描画を行わない。

#### 通知は使わない

ホーム画面に追加してもローカル通知・Web Pushは用いない（2.2）。PWA化の目的は起動性とオフライン動作に限る。

## 9. 決定事項の記録

| 決定 | 理由 |
|---|---|
| 記録アプリではなく実行アプリとする | 面倒さの本質は入力ではなく判断コストにあるため |
| ホームのカードタップは遷移のみ | 実際には構えてから開始するため、即開始は実態に合わない |
| 進捗グリッドを別画面に分離する | ホームの役割（今日やること）と情報の性質が異なり、情報過多になるため |
| 遡及入力を進捗画面に統合する | 実施し忘れた日の入力はテンポカウントを必要とせず、実行フローと噛み合わないため |
| 関門基準・解禁状態・級をレコードに保存しない | 常に導出可能なため |
| 当日目標・ステップ変更イベントは保存する | 復元不可能な状態・決定であるため |
| 級の移行時は前の級の総量を新セット数で割る | 飛び級が原理的に発生しない。書籍の進め方と一致する |
| ステップ昇格直後は初級基準の8割 | 動作が変わるため前ステップの実績から換算できない |
| 昇格提案は達成4回以上かつ4週以上 | 進行を止める方向にロジックを使う |
| 降格提案を設ける | 目標値を下げ続けてもステップ不一致は解決しないため |
| 片側種目は左右共通のステップ・級 | 左右別管理は書籍の進め方と合わず、進捗表示も倍増するため |
| 片側種目の達成は両側基準を満たした場合のみ | 弱い側に合わせ、左右差の拡大を防ぐため |
| `unit` と `mode` を独立させる | 回数系でもテンポカウントが適さない動作があるため |
| 通知機能を実装しない | Web Push実装のコストが個人利用に対して過大 |
| ストリークを採用しない | 途切れた際に離脱の引き金になるため |
| 週の目標回数を表示しない | 未達成の表示を作らず、実績のみを示すため |
| 解禁をハードロックにしない | 解禁条件の解釈に幅があり、実施を妨げる利益がないため |
| テンポを順序でなく意味で保持する | 種目により開始方向が異なり、順序で持つと上げ下げが入れ替わるため |
| テンポの種目別上書きを設けない | 書籍に種目別の秒数指定がないため |
| 音は毎秒ビープ＋レップ頭のみ変化 | フェーズごとに鳴らすと音の種類が増え、聞き分けが必要になる。テンポ変更にも追随できる |
| 級は色相、級内進捗は塗り面積 | 濃淡に両方を載せると境界が判別できないため |
| 昇格可能のみアクセント色 | 唯一の行動待ち状態であり、埋没させないため |
| セット完了時に±調整を設ける | 限界時に即座に終了操作ができないため |
| 中断時は未確定レコードを保存する | セット単位で保存しないと、離脱時に当日の実績が失われるため |
| 日付は開始時刻で確定する | 深夜をまたぐワークアウトで日付が分割されるのを防ぐため |
| 基準値をアプリに同梱しない | 書籍の基準表を再配布しないため。版差にも対応 |
| 設定に個別入力欄を設ける | JSON直接編集より実装量は増えるが、操作性を優先 |
| ファイルを分割する | 機能規模が単一ファイルの保守性を超えるため |
| オフラインでの起動を必須とする | 実行アプリである以上、ジムでその場で開けないことは機能欠損に等しいため |
| キャッシュはstale-while-revalidate | ビルド工程がなくファイル名にハッシュが付かないため。配信のたびに版を上げなくても更新が届く |
| 更新は自動適用せず明示操作とする | 実行中に再読み込みが起きるとテンポカウントが中断されるため |
| アイコンはSVGを原本とする | 版数を持たない静的サイトで、PNGの再書き出し元を残しておくため |
